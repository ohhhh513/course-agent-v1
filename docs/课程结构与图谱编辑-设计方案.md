# 课程结构管理与图谱手动编辑 · 设计方案

> 目标功能：① 教师新建章节/知识点；② 教师根据当前课程结构与知识点列表手动编辑图谱（前置关系）。
> 状态：待评审。评审通过后按"实施步骤"施工。

---

## 一、领域现状（设计依据）

| 事实 | 影响 |
| --- | --- |
| "章节"**不是节点**，是 `graph_nodes.chapter` 字符串字段（如"第1章"），散在每个 KP 行上 | 章无独立实体：无法建空章、重命名需批量 UPDATE、**排序依赖"第N章"文本 ASC**（教师自定义章名会乱序） |
| 三图谱共用 `graph_nodes`，联合主键 `(id, graph_type)`：knowledge 34 / problem 19 / goal 14 | 新增章/KP 必须带 graph_type，且 id 全局唯一 |
| 前置关系存了**两处**：`graph_links(relation='pre')` 与 `kp_details.pre_kp/post_kp`（JSON） | 编辑关系必须**双写**，否则详情页与图谱页不一致 |
| `kp_details` 每 KP 一行（难度/学时/摘要/资源/题数） | 建 KP 时需同步建 KpDetail 行 |
| 学习路径由图谱派生：`sync_user()` 只在 KP 集合变化时重建 | 结构 CRUD 后必须触发全员重建（机制已有） |
| 智能出题的 KP→王道小节映射（kp_section_mapping.json）按既有 KP 配置 | **新建 KP 没有题库映射**：智能出题对该 KP 覆盖为空（诚实边界，见 §六） |

## 二、两个核心设计决策

### 决策一：章节升为一等节点（复用现有表，零结构变更）

把"章"建模为 `graph_nodes` 中 `graph_type='chapter'` 的节点：

```
章节点：id = CH01/CH02…（全局自增），name = 章名，hours = 建议学时
KP 节点：id = KP074…（全局自增，现有 KP01–73）
         chapter 字段继续存章名（全链路兼容，学生端/资源中心零改动）
归属关系：KP.chapter === 章节点.name（同一事务内同步）
排序：章节点按 id（CH01 < CH02 …）天然有序，教师自定义章名不再乱序
```

| 对比 | 方案 A：章仍为字符串 | **方案 C：章为节点（选定）** |
| --- | --- | --- |
| 建空章 | 不可能（章是 KP 的属性） | ✅ 可以（先建章再填 KP） |
| 重命名 | 批量 UPDATE KP 行 | 改章节点 + 同事务同步该章 KP.chapter |
| 排序 | 依赖章名文本 | ✅ 章节点 id 有序 |
| 表结构/既有消费点 | 零改动 | 零改动（新类型只增不改） |

### 决策二：关系编辑以 `graph_links(relation='pre')` 为准，双写 KpDetail

- `PUT /kps/{id}/relations` 一次性覆盖式保存前置列表（贴合"编辑"心智）；
- 保存时 **环检测**（pre 边 DFS，边数 ≤ 数百，成本可忽略）；
- 同时同步 `kp_details.pre_kp / post_kp` 两个 JSON（详情页消费）；
- 删除 KP 时连带清理：links（双向）、KpDetail、全员学习路径该 KP 行；**有资源挂载或有题目 → 拒绝删除**（400，提示先迁移），避免悬空引用。

## 三、接口设计（teacher.py 新增"课程结构管理"区块，全部走课程上下文依赖）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/teacher/structure` | 结构页主数据：章节点列表 + 每章 KP（含 hours/is_key/前置数/资源数/题数） |
| POST | `/teacher/structure/chapters` | 建章 `{name, hours}` → 生成 CHxx |
| PUT | `/teacher/structure/chapters/{id}` | 改章名/学时（同步该章 KP.chapter） |
| DELETE | `/teacher/structure/chapters/{id}` | 删空章（章下仍有 KP 则 400） |
| POST | `/teacher/structure/kps` | 建 KP `{name, chapterId, hours, isKey}` → KPxx + KpDetail + 全员路径重建 |
| PUT | `/teacher/structure/kps/{kpId}` | 改名/换章/改学时/设重点（换章同步 chapter 字段） |
| DELETE | `/teacher/structure/kps/{kpId}` | 删 KP（有资源/题目 → 400；否则连带 links/KpDetail/路径行） |
| GET | `/teacher/structure/kps/{kpId}/relations` | 当前前置知识点列表 |
| PUT | `/teacher/structure/kps/{kpId}/relations` | `{preKpIds[]}` 覆盖保存（环检测 + 双写） |

**KP/章 id 生成规则**：查询当前课程该类型 id 的最大序号 +1（`KP074`、`CH10`…），冲突重试；跨课程全局唯一（主键约束）。

## 四、前端：教师端新导航页「课程结构」

```
┌─────────────── 左：章节树 ───────────────┐  ┌────── 右：选中 KP 编辑 ──────┐
│ [+ 新建章节]                              │  │ 名称 / 所属章节 / 学时        │
│ ▾ CH01 绪论 (2 KP)                        │  │ 是否重点 ☑                   │
│    • KP01 算法与复杂度   资源2 题8 [编辑]  │  │ 前置知识点：[多选下拉，覆盖保存] │
│    • KP02 时间复杂度分析 资源3 题5 [编辑]  │  │ 资源数 / 题目数（只读，供删除判断）│
│ ▾ CH02 线性表 (4 KP)          [+ 知识点]  │  │ [删除] （有资源/题时按钮禁用）  │
└──────────────────────────────────────────┘  └──────────────────────────────┘
```

- **不做拖拽画布**（起步版）：前置关系用多选下拉覆盖保存；学生端三大图谱**零改动**——数据变了自动"实时"。
- 删除 KP 的按钮在有资源/题目时禁用并显示原因（防误删）。
- 保存任何结构变更后：Toast 提示"已同步全体学生的学习路径"。

## 五、连锁影响与保障（CRUD 的每一次写入都要兼顾）

| 变更 | 自动连带 | 机制 |
| --- | --- | --- |
| 建/删 KP | 全员学习路径重建（新 KP=todo/res_count=0）；KpDetail 建立/删除 | `sync_user`（已有） |
| 建/改章 | KP.chapter 同步 | 同一事务 |
| 删 KP | links 双向删除、KpDetail 删除；**有资源/题目则拒绝** | 事务 + 前置校验 |
| 改前置关系 | 环检测 + KpDetail.pre_kp/post_kp 双写 | DFS + 同一事务 |
| 一切变更 | 资源上传弹窗、出题 KP 下拉、学生图谱**自动实时**（本就查库渲染） | 无需额外处理 |

## 六、诚实边界（做了也覆盖不到的）

1. **智能出题**：KP→王道小节映射表（`kp_section_mapping.json`）按既有 34 KP 人工维护，**新建 KP 没有映射** → 靶向练习/智能出题对新 KP 覆盖为空，需人工补映射（或后续做"映射管理页"）。
2. **RAG 题库切片**同样只覆盖既有 KP 的题；新 KP 的答疑检索依赖教师上传的课件切片。
3. 章节重命名会同步 KP.chapter，但**历史答疑会话/题目快照里存的旧章名文本**不会追溯更新（展示性残留，无功能影响）。
