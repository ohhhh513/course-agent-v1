### 2.2 三种"数据源"并存 —— 这是问题的根

| 数据源 | 位置 | 内容 | 课程隔离 | 谁在用 |
|---|---|---|---|---|
| 主库 | `backend/app/data/course_agent.db` | 课程/用户/资源/正式题库/会话/草稿（28 表） | ✅ 有 `course_id` | 全站业务 |
| RAG 库 | `backend/app/data/st/rag.db` | `chunks` 表（1514 切片 + 向量） | ⚠️ 半成品 | 两个 Agent 的检索 |
| JSON 题库 | `backend/app/data/st/st_bank/after_class.json` | 228 题原始题库 | ❌ 无 | Agent 的 `get_question` / `search_similar` |

**Agent 的"出题"实际横跨三个数据源**：从 JSON 读题骨架 → 从 rag.db 检索依据 → 写草稿到主库。三者的课程维度各不相同。

| 表 | 行数 | 课程维度 |
|---|---|---|
| `courses` | 1 | 唯一课程 `CDRJNVNW`「数据结构 · 2026秋季」 |
| `user_courses` | 2 | `Tbaiyin`(teacher) / `Sstudent`(student)，均属 `CDRJNVNW` |
| `questions` | 228 | ✅ `course_id='CDRJNVNW'` 全量归属 |
| `resources` | 65 | ✅ 带 `course_id` |
| `graph_nodes` / `graph_links` | 35 / 11 | ✅ 带 `course_id` |
| `kp_details` / `learning_paths` | 26 / 26 | ✅ 带 `course_id` |
| `chat_sessions` / `chat_messages` | 0 / 0 | ⚠️ 表有 `course_id`，但 Agent 写入时不填 |

**结论：主库的课程隔离地基是完整且干净的。** 无假数据污染，`questions` 228 题全部挂在真实课程下。

### 3.2 RAG 库 `rag.db`（9.4 MB，1 表 `chunks` 1514 行）

```
chunks 表结构：
  chunk_id TEXT PK · text · source_type · source_id · course_chapter
  section · question_id · page_or_slide · extra_json · embedding BLOB
  embedding_model · course_id TEXT NOT NULL DEFAULT 'C2026DS001'
```

**按 course_id 分布 —— 问题所在：**

| course_id | 切片数 | 在 `courses` 表里存在？ | 构成 |
|---|---|---|---|
| `CDRJNVNW` | 1024 | ✅ 是（真实课程） | ppt 794 + textbook 230 |
| `C2026DS001` | 490 | ❌ **否（孤儿 ID）** | **question_stem 228 + question_analysis 228** + ppt 1 + textbook 33 |

**按 embedding 分布 —— 两代混存：**

| embedding_model | 维度 | 切片数 | 对应 course_id |
|---|---|---|---|
| `local-hash-256` | 256 | 1024 | `CDRJNVNW`（全部资源切片） |
| `BAAI/bge-m3` | 1024 | 490 | `C2026DS001`（全部题库切片） |

**实测：按 course_id 过滤后能看到的切片数（副本上跑，未动原库）**

| 场景 | 不传 course_id<br>（教师出题当前行为） | 传 `CDRJNVNW`<br>（真实课程） | 传 `C2026DS001`<br>（孤儿） |
|---|---|---|---|
| explain 默认源<br>`question_analysis/textbook/ppt` | **1286** | 1024 | 262 |
| generate 默认源<br>`question_stem/question_analysis/textbook` | **719** | **230** | 489 |

> ★ **这张表是理解全局的钥匙**：
> - 教师出题流当前**不传 courseId**，所以能同时看到 `CDRJNVNW` 的教材 + `C2026DS001` 的题库解析 → "看起来能用"。
> - 一旦按多课程规范**正确传 `courseId=CDRJNVNW`**，可见切片从 719 **掉到 230**，**题库解析（456 条）全部消失** → 出题必然报"未检索到课程原文"。
> - 也就是说：**当前的出题功能是建立在"课程隔离失效"之上的**。这解释了为什么这个 bug 没被 E2E 发现。

## 五、确认的缺口清单

### P0 · 功能性缺陷（当前就错）

#### P0-1 教师端出题流完全没有课程上下文
- **证据**：`routers/teacher.py:1335-1340` 端点签名无 `course_id` 依赖；`:1414-1422` 构造的 `context` 无 `courseId`；`agent/tools/rag.py:54` 取到 `None`。
- **根因**：`docs/多课程最小重构方案.md` 的 Step 4「横向铺开」把 agent 链路归入"次要端点"，实际未迁移；同文档 §9 风险 #2 已自认列为待办。
- **影响**：① 出题检索跨课程全库混搜；② 不校验教师是否属于该课程，任何人传参即可触发。

#### P0-2 RAG 题库切片落在孤儿课程 ID 上
- **证据**：实测 490 条 `question_*` 切片全部 `course_id='C2026DS001'`，而 `courses` 表只有 `CDRJNVNW`。
- **根因**：三处默认值导致 —— `rag/ingest.py:99 ingest_bank()` 调 `ingest_path(path)` 不传 course_id；`routers/st_agent.py:73` `/agent/ingest/bank` 同样不传；`rag/store.py:57` 存量回填硬编码 `'C2026DS001'`。而后系统换课程时该 ID 未被同步。
- **影响**：见 §3.2 那张表 —— 一旦 P0-1 修好、出题流正确传 `CDRJNVNW`，题库切片可见数从 719 掉到 230，**出题功能会立刻报"未检索到课程原文"**。两个 P0 必须一起修。

#### P0-3 `delete_source_types` 缺少课程过滤 → 跨课程误删
- **证据**：`rag/store.py:81-91` SQL 只有 `WHERE source_type IN (...)`，无 `course_id`；`rag/ingest.py:81` 的 JSON 分支正是调用它。
- **影响**：任何一次题库重建索引（`/agent/ingest/bank` 或 `run_st_ingest.py`）都会**清空所有课程**的 question 切片。当前只有 1 门课尚不致命，多课上线即互相删除。

### P1 · 一致性缺陷（多课程语义不成立）

#### P1-4 Agent 创建的会话不写 course_id
- **证据**：`agent/store.py:47-50` `ensure_session` 未传 `course_id` → 走模型列默认值 `"C2026DS001"`（`models/ai.py:15`）；而 `routers/ai.py:48-51` 按真实课程的 `course_id` 过滤。
- **影响**：学生提问后左侧历史会话为空。

#### P1-5 出题草稿无课程维度
- **证据**：`models/agent_st.py` 无 `course_id` 列；`store.py:101-120 save_draft` 不写课程；`routers/teacher.py:1484 draft_list` 也不带课程过滤。
- **影响**：多课程下教师草稿箱混合显示。

#### P1-6 `rag.db` 与 pytest 临时产物被 git 跟踪
- **证据**：`git ls-files` 命中 `backend/app/data/st/rag.db`（9.4 MB）、27 个 `backend/data/.pytest-tmp-*/**/*.db|*.json`（3 轮测试残留）、8 个 `course_agent.db.bak.*`/`.before_*` 备份。`.gitignore` 里 `*.db`、`**/.pytest-tmp-*/` 规则**已存在**，但这些文件在规则生效前就已被跟踪，gitignore 对已跟踪文件无效。
- **影响**：这正是你说的"多人拉分支测试时数据堆积" —— 每次 `git pull` 会用仓库里的 rag.db 覆盖本地，团队成员各自的切片互相冲掉。

#### P1-7 embedding 向量两代混存
- **证据**：`local-hash-256`(256维) 1024 条 vs `BAAI/bge-m3`(1024维) 490 条；且仓库根目录**不存在 `.env`**（`LLM_API_KEY`/`EMBEDDING_API_KEY` 均空）→ `active_model_name()` 返回 `local-hash-256`。
- **影响**：① 真实课程的资源切片全是假向量，语义检索失效（维度不一致 → `cosine` 恒 0 → 退化为纯关键词）；② 反直觉风险：无 KEY 时调 `ensure_bank_indexed()` 会把 490 条**真的 bge-m3 向量降级覆盖**成 hash 向量，且因为 rag.db 被跟踪，这个降级会随提交永久固化。
- **附带**：无 `.env` 也意味着**当前两个 Agent 都跑在 demo 模式**（不调 LLM）。

### P2 · 卫生/设计项

| # | 问题 | 证据 |
|---|---|---|
| P2-8 | Agent 题库仍读 JSON 文件 | `rag/bank.py:12 load_questions()` 读 `st_bank/after_class.json`，带 `lru_cache` 进程级缓存，无课程维度 |
| P2-9 | 「防抄黑名单」有盲区 | `search_similar` 只扫 JSON 228 题；教师已发布的 AI 题（`q_id=AI***`）不在其中 → 可能重复出题 |
| P2-10 | 王道章节硬编码 | `rag/chapter_map.py:7 CHAPTERS` 写死 9 章映射，非课程化 |

## 七、适配方向（待讨论）

三个选项，可组合：

### 方案 A · 对齐既有机制（推荐）
把 `agent_st` 正式纳入"课程上下文"体系，与主库做法**保持同一套范式**：
1. **路由层**：`/question/gen` 加 `Depends(get_current_course_id)`；`/agent/ingest/*` 同样加依赖 + 课程校验。context 统一注入 `courseId`。
2. **落库层**：`chat_sessions.course_id` 由 `AgentStore.ensure_session` 显式写入；`st_question_drafts` 补 `course_id` 列。
3. **RAG 层**：`ingest_bank`/`ingest_path` 强制要求 course_id（去掉默认值）；`delete_source_types` 加课程条件；存量 490 条孤儿切片**重归属到 `CDRJNVNW`**（或按来源判别）。
4. **仓库**：`git rm --cached` 掉 rag.db 与 pytest 残留；提供 `run_st_ingest.py` 作为唯一重建入口，README 说明"RAG 库由本地构建、不入库"。

**优点**：与主库范式一致、可逐文件渐进、随时可停。
**代价**：需要决定"唯一课程 ID 来源"（`courses` 表 vs 硬编码默认值）。

### 方案 B · 最小止血
只修 P0-1/P0-2/P0-3，让单课程下功能真正正确；多课程语义留待后续。
**优点**：改动小、风险低、马上能用。
**代价**：多课程仍不成立，技术债继续累积。

### 方案 C · 彻底去 JSON 化
把 `rag/bank.py` 的题库来源从 `after_class.json` 改为读主库 `questions` 表（按 `course_id` 过滤），RAG 切片按 `res_id` 归属。
**优点**：彻底解决三数据源不一致；防抄黑名单覆盖已发布 AI 题。
**代价**：改动面最大，涉及 `get_question`/`search_similar`/`existing_ids`/`allocate_question_id` 全套；且 `questions` 表的 `q_id` 是字符串（`KHD***`/`AI***`），而 Agent 内部用整数 id，需要设计映射。
