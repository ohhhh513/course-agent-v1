# 多知识点（多 KP）与「关键词表课程化」改造方案

> 状态：**已于 2026-09-21 实施完成**（改动登记见《相较v1.0的改动.md》第六十节）。
> 最终采纳：① 定位 = 极简两层（读库术语匹配 + RAG 投票兜底，不加同义词表）；
> ② AI 题号 = `AI` + 8 位随机十六进制 + 唯一性重试；③ 多 KP 与题库管理侧对齐（`kp_id` = 主 KP）。
> 本文档保留决策依据与实测数据，供后续复盘。

---

## 一、现状核查

### 1.1 多 KP：主库与题库管理侧**已经完备**，缺口全在 agent 侧

| 环节 | 现状 | 证据 |
|---|---|---|
| 表结构 | ✅ 已有多 KP 列 | `questions.kp_ids` TEXT（`models/question.py:18`，注释即「可多；`kp_id` 保留为主 KP」） |
| 题目编辑接口 | ✅ 已写 kp_ids | `PUT /question/{q_id}`：`q.kp_ids = json_dumps(kp_list)`，`q.kp_id = kp_list[0]` |
| 批量导入 | ✅ 已写 kp_ids | `teacher.py:1907` |
| 题库列表返回 | ✅ 已返回数组 | `GET /question/bank` → `"kpIds": kp_ids` |
| 题库编辑界面 | ✅ 已支持多选 | `question.js:744` 读 `q.kpIds`，chip 可多选 |
| 出题页选 KP | ✅ 本就是数组 | `question.js:8` `gen: { kpIds: [] }` |
| 资源挂多 KP | ✅ 已在使用 | 65 个资源中 **15 个挂了多个 KP**（如 `R060/PPT_Ch09_插入与交换排序.pptx` = `["KP024","KP023"]`） |
| **agent 侧** | ❌ **9 处只认单 KP** | 见 1.3 |

**所以第 2 条不是"从零加功能"，而是"把主库已有的多 KP 能力贯通到 agent 侧"。**

### 1.2 关键词表：确实是硬编码，且代码里不该出现课程术语

`rag/topic.py` 的 `TOPIC_KEYWORDS` 是一张写死的 `(关键词, kp_id)` 表（约 70 条），直接引用 `KP010`、`KP020`
这类**课程专属编号**：换门课全部失效（`_fill_from_kp` 静默跳过，退化成只能靠章节定位），且教师改名后无人同步。

### 1.3 agent 侧单 KP 缺口（9 处）

| # | 文件 | 问题 |
|---|---|---|
| 1 | `rag/validate.py` | 只校验 `kp_id`；不认 `kp_ids`，也不校验「多 KP 是否同章」 |
| 2 | `rag/topic.py` | `resolve_topic` 只返回单个 `kp_id` |
| 3 | `rag/bank.py` | `to_agent_question` 不返回 `kp_ids`；`search_similar` 用 `row.kp_id != kp_id` **精确匹配单值**，挂多 KP 的题会漏 |
| 4 | `agent/tools/rag.py` | `retrieve_chunks` 工具只接受单个 `kp_id` |
| 5 | `rag/retrieve.py` | 同上 |
| 6 | `rag/store.py` | `load_filtered` 的 KP 过滤是单值 |
| 7 | `agent/tools/draft.py` + `agent/store.save_draft` | 校验只传单 `kp_id` |
| 8 | `routers/teacher.py:1636` | `draft_publish` 写 `kp_ids=json_dumps([kp_id])` —— **把多 KP 丢成单个** |
| 9 | `rag/ingest.py` `ingest_question_bank` | 题库切片只用 `q["kp_id"]`（`chunks` 表有 `kp_ids` 列却没用上） |

外加提示词 `skills/generate_items.md` 的 JSON 字段清单还是 `kp_id`。

## 二、定位方案：实测三选一

### 2.1 实验设置

24 条真实问法，逐条比对「期望 KP」与三种定位结果。`rag.db` 只读，`retrieve_chunks(top_k=20)`。
关键前提：**`rag.db` 1480 条切片 100% 带 `kp_id` 且 `kp_ids` 非空**（ppt 794 / textbook 230 / question_analysis 228 / question_stem 228）。

### 2.2 结果

| 方式 | 命中 | 说明 |
|---|---|---|
| **A. 关键词表（现方案）** | **23/24** | 但这是**针对本课程手工调过**的结果；换课程 = 0 分 |
| B1. RAG 投票，只用主 `kp_id` | 19/24 | 丢掉 `kp_ids` 里的其它 KP，票被带偏 |
| B2. RAG 投票，主 KP 全权 + 其余半权 | 19/24 | 半权压不住 |
| **B3. RAG 投票，`kp_ids` 等权** | **21/24**（Top-2 含期望 23/24） | **零配置、跨课程天然可用** |

单条耗时 **0.62s**（含 1 次 embedding 外网调用）。

### 2.3 两种方式各自失手在哪（关键）

**B3 失手 3 条，全部是「本课程没有该知识点的切片」或「上位 KP 抢票」：**

| 问法 | B3 | 原因 |
|---|---|---|
| KMP 怎么求 next 数组？ | KP009（串） | 精确层 KP010「串的模式匹配」**是 6 个无题 KP 之一**，几乎没有专属切片；同章上位 KP 抢票。**Top-2 含 KP010 ✓** |
| 红黑树 | KP013/KP015 | 红黑树**不在本课程 26 个 KP 内**，库中无对应切片 → B 只能瞎猜 |
| 顺序表和链表 | KP003（线性表） | 双主题，**Top-2 含 KP005 ✓** |

**A 失手 1 条**：「顺序表和链表」→ KP004（只能给一个 KP）。A 的强项恰是 B 的弱项：**短术语的精确匹配**。

> **重要发现**：B 的失手全部落在「A 只要有一行同义词就能救」的场景；而 A 的失手（双主题、自然语言长句）恰是 B 的强项。
> 两者互补，不是替代关系。

### 2.4 结论：三层定位（全部数据驱动，代码零课程术语）

```
1) 显式信号（最高优先，现状保留）
   题号 q_id / 知识点 kp_id / 章 chapter_id —— 来自前端选择或上下文

2) 术语匹配（读库，长词优先）
   2a. 知识点名称：直接拿 graph_nodes.name 匹配
       ← 这就是「该课程真实的关键词表」，无需任何额外配置
   2b. 同义词表（可选，kp_keywords）：KMP→串的模式匹配、BST→树形查找
   命中即采信（可解释、可与教师对齐）

3) RAG 投票兜底（读 rag.db）
   前两层没命中（uncertain）时：检索 top-20 → 按切片的 kp_ids 等权聚分 → 取 Top-K
   用于：自然语言长描述、表里没有的说法、双主题（Top-2 正好喂给多 KP）
```

**为什么 2a 就够"不同课程得到真实关键词表"**：
「树形查找」「二叉树遍历」「最短路径与生成树」**本身就是知识点名称** —— 26 个 KP 名就是这门课的术语表，
且它天然按课程存在 `graph_nodes` 里。实测「树形查找」「查找」「二叉树遍历」「图的遍历」全部靠名称匹配即可命中。
代码里从此不出现 `KP0xx`。

**2b 的意义**：`KMP`/`BST`/`B树` 这类**缩写与外文**无法靠中文名称匹配，只能靠同义词表。

**效率红利**：`explain` 流本来就要调 `retrieve_chunks` 取证据。把定位与检索**合并**（先不限 KP 检索 →
用命中投票定 KP → 这些命中直接当证据），**省掉一次 embedding 调用**（约 0.6s/轮），也避免了"定位错了就检索不到"。

### 2.5 需注意的口径问题

- 投票要用切片的 **`kp_ids`**，不能用 `kp_id`（主 KP 只取首个 → 实测掉 2 分）
- 需要**置信度门槛**：绝对票分过低或 Top1/Top2 接近时，应保持 `uncertain` 并给出候选，不要硬指
  （例：「红黑树」票分 2.43 远低于「树形查找」的 7.33，可据此判低置信）。阈值需再复测。
- 若采用第 3 层，`MIN_RETRIEVE_SCORE`（现 0.12）与投票门槛要一起标定

## 三、题号：AI 草稿号当前是「全库自增」（实测）

### 3.1 实测行为

| 顺序 | 操作 | 得到 |
|---|---|---|
| 1 | 课程 A 第 1 道 AI 题 | `AI001` |
| 2 | **课程 B 第 1 道 AI 题** | **`AI002`** ← 不是 AI001 |
| 3 | 课程 A 第 2 道 AI 题 | `AI003` |

原因：`questions.q_id` 是**主键**（`answer_records.q_id` / `tags.q_id` 外键引用它），
所以必须**全局唯一**；`next_ai_q_id` 因此扫全库 `AI%` 自增，不按课程分段。

**后果**：① 题号不可读（本课只有 1 道 AI 题却叫 AI002）；② 号段被其他课程吃掉；③ 依赖全表 `LIKE` 扫描。

### 3.2 三个选项

| 选项 | 形态 | 优点 | 代价 | 改动面 |
|---|---|---|---|---|
| **① 与主库统一（推荐）** | `Q` + 8 位十六进制，如 `Q8FE3AE1` | 与主库 228/228 完全一致；随机不撞号，**去掉全表扫描**；无"从 002 开始"的怪相 | 题号里看不出是不是 AI 出的（靠 `source_ref_file='ai_draft'` 溯源） | `bank.next_ai_q_id`、`draft_publish` 兜底、提示词已改好 |
| ② 保留 AI 标识 | `AI` + 6 位十六进制，如 `AI3F8A21` | 一眼可辨 AI 题；不撞号 | 不如序号直观 | 同上 + `validate.Q_ID_RE` |
| ③ 维持现状 | `AI` + 全局 3 位序号 | 改动最小；序号连续易读 | 需接受「第二个出题的课程首题是 AI002」 | 无 |

> 三种都不影响已发布数据（当前 `AI` 号 0 条，无历史包袱）。

## 四、改动清单与分批

### 第一批 · 定位改造（第 1 条）

| 文件 | 改动 |
|---|---|
| `rag/topic.py` | 删除 `TOPIC_KEYWORDS` 硬编码；改为「名称匹配（读 `graph_nodes`）+ 同义词表（读库）」；命中可返回 **多个** KP |
| 新增 `rag/keywords.py` | `match_by_term(course_id, text)`（名称 + 同义词，统一按长度降序 + priority）、`vote_by_retrieval(course_id, query)`（读 rag.db 投票） |
| `rag/retrieve.py` | 支持不限 KP 检索（供投票用），并返回 `kp_ids` |
| `agent/tools/rag.py` | 检索与定位合并：命中可用作证据 |
| `routers/teacher.py` | 新增 `GET/POST/DELETE /structure/kp-keywords`（**仅在做 2b 同义词表时需要**） |
| 一次性 seed | 把 `KMP→KP010`、`BST→KP020` 等同义词灌成 `CDRJNVNW` 初始数据 |
| `loader.py` / `skills/explain.md` | 把本课「知识点清单」注入 system prompt；one-shot 里的具体编号改为注入驱动 |
| `tests` | 名称匹配、长词优先、同义词、RAG 投票、跨课程不串 |

### 第二批 · 多 KP 贯通（第 2 条）

按 1.3 的 9 处逐项改造（`kp_id` = 主 KP，`kp_ids` = 完整列表；检索按并集）。
配套测试：多 KP 校验、成员匹配不漏题、发布保留多 KP、检索并集。

### 第三批 · 教师端界面（可选）

知识点详情弹窗加「检索关键词」编辑区（动 `structure.js`）。
若第一批采用**无同义词表**的极简版（仅名称匹配 + RAG 投票），则第三批完全不需要。

## 六、风险与影响面

| 风险 | 说明 | 应对 |
|---|---|---|
| 定位口径变化影响答疑质量 | 从"硬编码表"改为"名称 + 检索投票"，命中集合会变 | 已备 24 条对照用例，改造后逐条复测并列出修前/修后 |
| RAG 投票需多一次外网调用 | 0.62s/次（若能合并进现有检索则无额外成本） | 定位与证据检索合并；投票用已取回的命中 |
| 低置信误判 | 「红黑树」这类课程不覆盖的术语会被硬指到邻近 KP | 加置信度门槛，不足则保持 `uncertain` + 给候选 |
| 多 KP 改变检索范围 | 并集会让命中变多、分数分布变化 | 复测 `MIN_RETRIEVE_SCORE`；必要时按主 KP 加权 |
| 历史题 `kp_ids` 为空 | 已发布的 228 条只有 `kp_id` | 不回填（逻辑兼容）；新题起用多 KP |
| 新增表（若做同义词表） | 首启自动建表 | `create_all` 幂等，无需迁移脚本 |
