# 项目真实交互梳理（前后端 · 数据库）

> 审计方式：静态代码通读（routers / services / models / agent_st 全部文件）+ 数据库快照实测（`course_agent.db`、`st/rag.db` 逐表计数）+ 运行时配置核对（`.env` / `.gitignore`）+ 文档与代码对照。
> 审计基线：`2026-09-11` 工作区快照。本文件记录审计时点的真实状态，后续文档治理见《相较v1.0的改动.md》。
> 结论口径：本文只回答「**这条链路现在到底连的是真的还是假的**」，不评价设计好坏。

## 〇、一句话结论

项目**不是简单的"一半真一半假"**，而是四种性质叠加在一起，肉眼很难区分：

| 层 | 性质 | 表现 | 规模 |
| --- | --- | --- | --- |
| **L1** | 真实实现 + 真实数据 | 打开就能看到正确内容 | 学生端/教师端大部分页面 |
| **L2** | **真实实现 + 数据空转** | 代码是真算法，但输入数据几乎为空 → 页面显示 0 / 空列表，**看起来像假的** | 掌握率、预警、归因、干预、报告 |
| **L3** | 真实实现 + 双模式降级 | 有 Key 走真实 LLM，无 Key 走假流式 | AI 答疑、AI 出题 |
| **L4** | 纯占位 | 硬编码返回 / TODO | 素材上传、答疑反馈、靶向补练包 |

**最危险的是 L2**：它既不是 bug 也不是占位，代码完全正确，但因为 `learning_paths` 表 408 条**全部是 `todo`**、`answer_records` 只有 **2 条**，导致整个"学情/预警/归因"体系在**空转**。接手者很容易误判成"这些功能没做"或"这个模块坏了"。

而 **L3 有一个当前状态的关键事实**：`backend/app/.env` **存在且配好了真实密钥**，所以现在实际跑的是 **live 模式（真实 DeepSeek 调用）**，不是演示模式。

## 一、真实调用链总览

### 1.1 前端 → 后端

```
浏览器 (student.html / teacher.html)
   │  仅作外壳，<script src> 加载 assets/js/**
   ▼
assets/js/api.js    ← 唯一数据层，config.mode = 'http'，baseURL = '/api/v1'
   │  普通请求: fetch + JWT
   │  流式请求: streamRequest() 手动解析 SSE
   ▼
FastAPI (/api/v1/**)  ← backend/app/main.py 注册 12 个 router
```

**关键点**：`api.js` 里仍保留了一整套 `mock` 分支（`const M = () => window.MOCK`，第 127 行），但 `assets/js/mock/` 目录**已被删除**，`window.MOCK` 永远 `undefined`。因此 **`api.js` 中 30+ 个 `resolver` 回调全部是死代码**，只有 `config.mode='http'` 那条分支在跑。

### 1.2 后端分层

```
routers/*.py        路由层：鉴权、参数校验、组装 camelCase 响应
   │
   ├── services/*.py      业务服务层（算法）
   ├── models/*.py        ORM（23 张表）
   └── agent_st/          RAG + LLM 智能体运行时（独立子包）
          ├── agent/runtime.py   编排（live / demo 双模式）
          ├── agent/tools/*      7 个工具
          └── rag/*              检索、切片、embedding
```

### 1.3 两个独立数据库

| 库 | 路径 | 大小 | 用途 | 谁在写 |
| --- | --- | --- | --- | --- |
| 主库 | `backend/app/data/course_agent.db` | 744 KB | 全部业务数据 | `routers/*` 经 SQLAlchemy |
| RAG 库 | `backend/app/data/st/rag.db` | 9.4 MB | 向量切片（1480 chunks） | `agent_st/rag/ingest.py` |

**两库之间没有外键、没有 JOIN、没有跨库读取**，唯一的弱关联是"**约定相同的题目 ID**"（`after_class.json` → `questions.q_id` = `KHD###`，同时被切进 rag.db 的 chunk 元数据）。这是一个**隐式契约**，不是数据库约束。

**当前判定：`chat_available()` 返回 `True`**（`backend/app/.env` 已配置 `LLM_API_KEY` / `EMBEDDING_API_KEY`），**所以现在是 live 模式，AI 答疑与出题是真实的**。
`GET /agent/status` 会返回 `{mode:"live"}`，可直接用它现场验证。

**补充事实（深度审计）**：

- **降级是真分支，不是写死**。`runtime.py:236` 依据 `chat_available()`（`llm.py:13-15`）分流；配 Key 后确实走 HTTP（`llm.py:69` `chat.completions.create`、`embed.py:99` `embeddings.create`）。demo 的假只是"文本来源"假，**检索仍是真实的**。
- **agent_st 对主库主题库零直接耦合**：`agent_st/**` **不 import `models.question`**，从不读主库 `questions` 表；它只读 `after_class.json`。把草稿写进正式题库的唯一入口是 `teacher.py:1456`（草稿发布），**位于主模块内**——这是一个需要人工审核权限把关的跨模块耦合点。
- **`ai_samples.json` 与 agent_st 无关**：agent_st 运行时根本不加载它，它只被 `services/bootstrap.py` 用来给主库播一条 `AI001`。别把它当 Agent 的数据源。
- ⚠️ **一个隐藏的检索退化风险**：rag.db 的向量维数取决于**建库时**用的 embedding。若建库时配了远程 `EMBEDDING_API_KEY`（bge-m3，1024 维），而运行时**没配** Key，查询向量会变成 `local-hash-256`（256 维），**维数不匹配 → 余弦相似度恒为 0 → 自动退化成纯关键词打分**（`retrieve.py:52-55`）。此时"demo 模式真实检索"的说法只剩关键词检索。需靠 `ensure_bank_indexed` → `reembed_stale_chunks` 重算才能恢复语义检索。
- 草稿另有 sidecar 落盘：`backend/app/data/st/drafts/`（每份草稿一个 JSON），仅调试用，已被 `.gitignore` 忽略。
- 越界阈值 `OFF_TOPIC_SCORE = 0.28`（`config.py`）偏低；代码已用"看最高分"而非"有命中即相关"来缓解（`runtime.py:181-194`），但仍可能把生活类问题误判为课程内。

## 四、真假模块之间的耦合点（重点）

这是"真假混杂导致混乱"的**技术根因**——真模块的输出依赖假/空模块的输入：

| # | 耦合 | 方向 | 后果 |
| --- | --- | --- | --- |
| 1 | `alert_detector` ← `answer_records` | 服务 → 空表 | 预警检测是**真算法**，但 `answer_records` 只有 2 条 → `alerts` 恒为 0 |
| 2 | `student.mastery/*` ← `learning_paths.mastery` | 路由 → 全 todo 表 | 掌握率全 0，级联影响雷达/矩阵/对比 |
| 3 | `intervention._generate_interventions_from_db` ← `learning_paths` | 干预 → 全 todo 表 | 阈值 `avg<50 且 started>=3` **永不满足** → 干预列表为空 |
| 4 | `analysis/errors|weak-chain|causes` ← `answer_records` | 归因 → 2 条记录 | 三张归因图恒为空 |
| 5 | `report/generate` ← 上面全部 | 报告 → 全空 | 报告章节有结构、无内容 |
| 6 | `ai.py` / `teacher.py` → `agent_st.runtime` | 真路由 → 真 Agent | **这是全项目耦合最健康的一条**：真实 LLM |
| 7 | `agent_st` ← `after_class.json` 与 `questions.q_id` | 隐式 ID 契约 | 无外键，靠命名约定，改一处会静默失配 |
| 8 | `api.js` mock 分支 ← `window.MOCK` | 死耦合 | 目录已删，分支永不可达 |
| 9 | `student` ↔ `graph` ↔ `practice` | **私有函数级** | 跨 router 直接 import 对方的**私有函数**：`student.py:87` 用 `graph._mastery_for_user`、`teacher.py:33` 用 `practice._calc_question_stats`。改一处会静默影响多处，是"真假混杂"蔓延的通道 |
| 10 | `question.js:558` → `/question/import/file` | **前端绕过数据层** | 全项目唯一一处不走 `API.*` 而直接 `fetch` 的调用，因此也没拿到统一注入的 token（见 §六） |

**一句话**：`answer_records` 和 `learning_paths` 这两张"数据地基表"一旦为空，所有上层"智能分析"模块全部退化成空壳——**但它们并非假实现，只是没有粮食**。

## 七、建议的整理顺序

**第一步 · 把"空转"和"占位"分开标注**（成本最低、收益最大）
避免后来者把 L2 误判成 bug。

**第二步 · 补数据地基，而不是改代码**
`learning_paths` 与 `answer_records` 是全部"智能分析"的输入端。造一批合理的答题记录（哪怕脚本合成），能让预警/归因/掌握率/报告**同时从"看起来是假的"变成"看得出是真的"**。

**第三步 · 修掉唯一的硬 bug + 清理真假重复实现**
- **先修 `question.js:558` 的 token bug**：改为走 `API.*` 统一层（或至少读 `ca_session.token`），否则教师端文件导入永远 401；
- 删除 `api.js` 的 mock 分支（含 `mockAnswer`、`ACCOUNTS_KEY` 等约 200 行死代码）；
- 决定 `/question/materials` 与 `/question/import/file` 保留哪一个，删掉另一个；
- `/ai/feedback`、`/question/packs` 要么实现要么移除；
- 清掉僵尸表 `teacher_class_data` 与死数据 `MOCK_ANSWER_RECORDS` / `MOCK_QUESTIONS`，或明确其用途。

**第四步 · 统一文档口径**（本次已执行）

**第五步 · 修仓库卫生**
`git rm --cached` 掉 `rag.db`、`.pytest-tmp-*`、`.bak.*`，并确认 `.gitignore` 规则对**已追踪文件**是否生效（ignore 对已追踪文件无效，必须先 `--cached` 移除）。
