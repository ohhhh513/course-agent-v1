## 二、核心规范：章节 + 知识点

**课程结构由 `graph_nodes` 一张表承载，靠 `graph_type` 区分两类节点。**

### 2.1 复合主键（重要）

`graph_nodes` 的主键是 **`(id, graph_type)` 复合键** —— 同一个 `id` 可以在不同类型下重复存在，因此**任何查询都必须同时带 `graph_type` 和 `course_id`**。

### 2.2 章节（`graph_type='chapter'`）

| 列 | 含义 | 实际值 |
|---|---|---|
| `id` | 章节 id | `CH01` … `CH09` |
| `name` | 章节名 | `第1章 绪论` … `第9章 排序` |
| `chapter` | 恒为空（章节节点不用此列） | `''` |

### 2.3 知识点（`graph_type='knowledge'`）

| 列 | 含义 | 实际值 |
|---|---|---|
| `id` | 知识点 id | `KP001` … `KP026` |
| `name` | 知识点名 | `数据结构概述`、`二叉树遍历` … |
| `chapter` | **所属章节名（字符串）** | `第6章 树和二叉树` |
| `difficulty` | 难度 1~5 | 现均为 2 |
| `is_key` | 是否重点 | 现均为 0 |
| `pos_x` / `pos_y` | 图谱编排坐标 | 已布点 |

### 2.4 章节 ↔ 知识点的关联方式

**关联键是「章节名字符串」**，不是 id，也没有外键：

```sql
-- 取某章的全部知识点
SELECT * FROM graph_nodes
WHERE graph_type = 'knowledge' AND course_id = ? AND chapter = '第6章 树和二叉树';
```

> ⚠️ 这是当前唯一可用的关联方式。实测 26 个知识点的 `chapter` 全部能对上 9 个章节节点的 `name`。
> 若将来要改成按 id 关联，需新增列并由教师端编辑入口同步维护。

| 列 | 含义 |

### 2.7 知识点详情（`kp_details`）

`kp_id` 为主键，冗余承载 `name` / `chapter` / `difficulty` / `pre_kp` / `post_kp` 等。
`graph_nodes` 是**结构权威**，`kp_details` 是**其扩展与统计位**。

> ⚠️ `kp_details.question_count`、`wrong_count`、`mastery_rate` 等统计字段**当前全为 0，不可信**，
> 需要统计时请实时聚合 `questions.answer_records`，不要读这些列。

## 三、内容表如何引用章节/知识点

| 表 | 章节字段 | 知识点字段 | 备注 |
|---|---|---|---|
| `questions` | `chapter_id` = `CH01..CH09`<br>`chapter` = 章名 | `kp_id` = 主 KP（单值）<br>`kp_ids` = JSON 数组（**当前全空**） | `kp_path` = `["章名","知识点名"]`，供展示 |
| `resources` | `chapter_id`、`chapter` | `kp_id` = 主 KP<br>`kp_ids` = JSON 数组（**65/65 都有值**） | 资源可挂多 KP |
| `learning_paths` | `chapter` | `kp_id` | 一人一行 · 26 行 |
| `answer_records` | —（经 `q_id` 关联） | `kp_id` | 答题记录 |
| `alerts` | —（经 `class_id`） | `kp_id` / `kp_name` | 预警 |

**查询范式（推荐写法）**：

```sql
-- 某课程的「章 → 知识点」树
SELECT c.id AS chapter_id, c.name AS chapter_name,
       k.id AS kp_id, k.name AS kp_name
FROM graph_nodes c
JOIN graph_nodes k
  ON k.graph_type = 'knowledge' AND k.chapter = c.name AND k.course_id = c.course_id
WHERE c.graph_type = 'chapter' AND c.course_id = :course_id
ORDER BY c.id, k.id;

-- 某知识点的题目
SELECT q_id, stem, difficulty, status FROM questions
WHERE course_id = :course_id AND kp_id = :kp_id AND status = 'published';

-- 某知识点的资源（多 KP 命中用 LIKE，注意 JSON 引号）
SELECT res_id, title, type FROM resources
WHERE course_id = :course_id AND kp_ids LIKE '%"' || :kp_id || '"%';
```

> `kp_ids` 是 JSON 文本。当前无 JSON1 扩展依赖，用 `LIKE '%"KP001"%'` 即可；若要精确匹配建议后续改用 `json_each`。
>
> **接口口径（2026-09-22 统一）**：`GET /student/resources?kpId=`、`GET /graph/kp/{kpId}` 的 `resources`、
> `GET /teacher/graph/kp-detail` 的 `resourceCount` 一律按 **`kp_id` 命中 ∪ `kp_ids` 命中**过滤
> （`services/catalog_helpers.resource_hits_kp()`），与学习路径 `resCount`（`learning_path.resource_count_map()`）同源，
> 保证「左侧标记 N 个资源」＝「点进去看到的条数」。
> 只写上面那条 `kp_ids LIKE` 会漏掉"主 KP 就是本知识点、但没写进 `kp_ids`"的历史数据，实现请取并集。

## 四、课程隔离要求（强制）

| 规则 | 说明 |
|---|---|
| 必带 `course_id` | 所有业务表查询必须显式过滤 `course_id`，**禁止**「不传就是全库」 |
| `course_id` 不给默认值 | 模型层历史默认值 `C2026DS001` 是孤儿课程，是串数据的根因。新列一律不给默认值 |
| 课程上下文来源 | 请求头 `X-Course-Id` → `dependencies.get_current_course_id()` → 查 `user_courses` 并做成员校验（非成员 403） |
| 会话/草稿 | `chat_sessions.course_id`、`st_question_drafts.course_id` 由写入方显式提供 |
| 无归属用户 | `user_courses` 无记录 → **400**，绝不回退到演示课 |

**已具备 `course_id` 的表**：`courses`(PK) · `user_courses` · `resources` · `questions` · `graph_nodes` · `graph_links` · `kp_details` · `learning_paths` · `answer_records` · `practice_sessions` · `chat_sessions` · `st_question_drafts` · `alerts` · `tags` · `reports`(经 class_id)

**经关联间接隔离**（不加列）：`chat_messages`（经 session）· `resource_progress`（经 resource）· `question_tags`（经 q_id）· `resource_tags`（经 res_id）

**个人/全局数据**（暂不隔离）：`users` · `classes` · `teacher_classes` · `teacher_class_data` · `messages` · `study_checkins` · `resource_study_log` · `intervention_templates` · `interventions`

## 五、用户与课程归属

```
users ──< user_courses >── courses
                role_in_course: teacher | student
```

- `users.user_id` 是业务主键（如 `Tbaiyin` / `Sstudent`），`username` 唯一索引用于登录。

- 教师建课时会写入 `courses` + `user_courses(role=teacher)`；学生凭 `courses.invite_code` 入课。

## 六、AI 层（agent_st 相关）

| 表 | 说明 |
|---|---|
| `chat_sessions` | 一次答疑会话。`session_id` PK（`CH`+hex）、`user_id`、**`course_id`**、`title`、`flow_id`、`rounds` |
| `chat_messages` | `session_id` + `role`(`me`/`ai`) + `content` + `citations`(JSON) + `tool_log`(JSON) + `draft_id` |
| `st_question_drafts` | 出题草稿。`draft_id` PK（`QD`+hex）、`user_id`、**`course_id`**、`batch_id`、`payload_json`、`status`(`draft`/`invalid`/`published`)、`errors_json` |

**隔离键**：会话与草稿都是 `user_id + course_id` 双维。前端历史会话列表按 **学生 id** 汇总（跨课程可见），出题草稿列表按 **course_id** 过滤。

### 6.1 知识点定位（`rag/topic.py`，2026-09-21 改造）

**代码里不允许出现任何课程专属术语（如 `KP020`、某个知识点名称）。** 定位分两层，都从库里取数据：

| 层 | 数据来源 | 说明 |
|---|---|---|
| 1. 术语匹配 | 主库 `graph_nodes.name` | **知识点名称本身就是本课术语表** —— 「树形查找」「二叉树遍历」都是 KP 名，直接拿名称匹配即可，无需教师额外配置。匹配按 **名称长度降序**，并把已命中片段从待匹配文本中挖掉，所以「树形查找」命中后不会再被「查找」抢一次；而「栈和队列」会同时命中两个 KP |
| 2. RAG 投票兜底 | `st/rag.db` 切片 | 术语层没命中时（自然语言长描述），用检索命中切片投票：**按切片的 `kp_ids` 等权累计得分** |

**投票必须用 `kp_ids` 而非 `kp_id`** —— 切片只把主 KP 写进 `kp_id`，用它投票会漏掉「插入与交换排序」这类挂多 KP 的课件（实测掉 2 分）。

**置信度门槛**：最高票 < `VOTE_MIN_SCORE`(2.0) 时保持 `uncertain` 并给候选，不硬指；Top1 得分不足 Top2 的 `VOTE_TOP1_RATIO`(1.6) 倍时视为并列（双主题），两个都取。

**定位优先级**（`resolve_topic`）：显式 `q_id` > 显式 `kp_id` > 显式 `chapter_id` > 文本中 `KP0xx` > 文本中 `CH0x` > 「第N章」 > 术语匹配 > RAG 投票。

### 6.2 多 KP 语义（与题库管理侧对齐）

```
kp_id   = 主 KP（kp_ids 首个）—— 组卷、掌握度、统计一律用它
kp_ids  = 完整列表（JSON 数组）—— 可多项、可跨章
```

- 出题时 `resolve_topic` 返回的 `kp_ids` 直接作为题目的考查知识点；模型输出 `kp_ids` 数组，单考点写一项。
- **校验**：每个 KP 都必须属于本课程图谱；**主 KP 必须与 `chapter_id` 自洽**，其余 KP 不要求同章
  （如「二叉树和图的区别」会命中跨章的两个 KP，这是合法场景）。
- **检索/防抄一律按成员匹配**（`kp_id ∈ 题/切片的 kp_ids`），否则挂多 KP 的题会被漏掉。
- 挂载方式：主 PK 在 `kp_id` 列（单值）+ 完整列表在 `kp_ids`(JSON) —— `questions`、`resources`、RAG `chunks` 三处一致。

## 七、题号（`q_id`）体系

`q_id` 是 `questions` 的主键，是**系统生成的字符串**，前后端一律当**不透明标识**使用（前端对其无任何前缀假设，纯展示）。

| 前缀 | 生成位置 | 形态 | 当前实况（2026-09-21） |
|---|---|---|---|
| `Q` + 8 位十六进制 | 教师端新增 / 导入题库（`routers/teacher.py` 的 `"Q" + uuid4().hex[:8].upper()`） | `QD44D2820` | **228 / 228 条全部是这种** |
| `AI` + 8 位十六进制 | AI 草稿发布（`bank.next_ai_q_id`） | `AI3F8A21E7` | 0 条（规则已实现，尚未发布过） |
| `KHD` + 3 位 | 旧 `import_st_bank.py` 导入 after_class.json | `KHD001` | **0 条，该路径已退役** |

### 7.1 分配规则（强制）

1. **`q_id` 不是 Agent 的输出字段。** 模型的出题 JSON 里不应出现 `q_id`；保存时由 `save_question_draft` 分配。
2. AI 题号 = **`AI` + 8 位随机十六进制**（与教师端的 `Q` 前缀区分，一眼可辨是 AI 生成的题）。
   **不再自增**：`q_id` 是主键、必须全局唯一，自增就得扫全库 `LIKE 'AI%'`，于是「第二门出题的课程第一道题」
   会拿到 `AI002`（号段被别的课程吃掉），且号段越大越慢。
3. **随机 hex 必须配合唯一性检查**：16^8 ≈ 4.3e9，按 1 万道题估算出现一次碰撞的概率约 1% —— 不是 0。
   所以 `next_ai_q_id(course_id, reserved=...)` 会检查「正式题库已有 AI 号 ∪ `reserved`（本批草稿已占的号）」，
   撞了就换一个。**不要退回纯随机或纯自增。**
4. `validate_question` 对 `q_id` 的要求：**缺失不算错**（保存时补），但一旦给了值就必须匹配 `^[A-Za-z]{1,4}[0-9A-Za-z]{3,12}$`。
   注意前缀之后要允许**字母数字混合**（`QD44D2820` 就是 `Q` + 十六进制），只写 `\d` 会误杀主库全部题号。
   这样也能挡住模型把提示词示例串（如 `AI###`）当题号写进 JSON 的情况。
5. 发布（`draft_publish`）优先复用草稿里已分配的号；为空或与正式题库撞号时才调 `next_ai_q_id` 重新分配
   （**同一实现，不另写一份**）。

### 7.2 引用格式

Agent 在讲解里引用题号时使用 `[题号 {q_id}]`，必须**原样照抄**工具返回的值（如 `Q8FE3AE1`），不得改写、补零或缩短。

**判定依据**：`kp_section_mapping.json`（28 个小节 → 29 个 `KP01/KP51/KP401` 旧编码）与当前图谱
`graph_nodes`（26 个 `KP001..KP026`）**交集为 0**，该映射早已完全失效。

### 新架构要点

- **`rag/figures.py`**：图类型闭集与 `figure_mode` / `extra_from_question`（纯函数，不碰数据库）。
- **`rag/structure.py`**：课程结构查询唯一入口（`list_chapters` / `list_kps` / `kp_info` /
  `valid_kp_ids` / `chapter_id_by_name` …），直读 `graph_nodes`，不缓存。
- **`rag.db` 切片结构**：`course_id` + `chapter_id` + `kp_id` + `kp_ids` + `q_id` + `source_id`。
  结构归属**继承来源表**：资源切片继承 `resources`，题库切片继承 `questions`，**不做任何文本推断**。
