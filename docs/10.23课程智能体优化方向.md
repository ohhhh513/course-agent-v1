## 一、管理员退绑课程后，未通知被退绑的教师（待补）

### 现状与问题

2026-10-22 解开课程删除死锁时，本次只做了「管理端可直接退绑负责人」这一半；你原始需求里的另一半 —— **「向教师发出删除课程通知，通告教师退绑课程」** —— 经确认本次不做，先记在这里。

当前退绑是**管理员单方面动作**，被退绑的教师端**收不到任何提示**：

- 教师登录后看到的课程列表里，那门课**直接消失**，没有任何说明；
- 他若此时对这门课发起操作（建资源、传教材、答疑），会被权限校验拒绝（`routers/teacher.py` 按 `user_courses.role_in_course == "teacher"` 判定成员身份）；
- 报错是通用的「无权访问该接口」/「你尚未加入课程」，教师**无从判断**是权限被收回、还是课程被删了、还是操作写错了。

也就是说：功能上是自洽的，但对被退绑的那一方是「无预告的静默失权」。这是本次刻意接受的取舍，不是遗漏。

### 建议的做法（按代价从低到高）

**方案 A · 只加站内提示，不做主动推送（推荐先做）**

在教师端课程列表 / 驾驶舱顶部，对「`courses.owner_id` 仍指向自己、但 `user_courses` 里已无自己」这种情况渲染一条说明条，文案类似「你已被移出《课程名》的授课绑定，该课程已交由管理员重新指派或删除」。纯读现有两列，不加表、不加列、不写迁移脚本，一次查询即可算出，成本最低。

**方案 B · 退绑时留一条系统消息给教师**

在退绑动作发生时写入一条给该 `user_id` 的消息（复用项目已有的消息/公告表），教师登录后在消息中心看到「管理员已将你移出《课程名》」。同样不改表结构，但需要确认复用哪张现有表、以及教师端消息中心的现有取数口径。

**方案 C · 「待确认退绑」两阶段（最完整，也最复杂）**

管理员点退绑 → 课程进入 `pending_unbind` → 给教师发通知 → 教师确认后成员关系才真正删除。管理员在确认前可撤销。体验最完整，但需要新增状态存储，且要考虑「教师长期不登录导致课程卡在 pending」怎么办 —— 是否设超时自动生效。

### 动手前需要先确认的点

1. 走 A / B / C 哪一个？是否先做 A 止血？
2. 若做 B，复用现有哪张消息表？（本次未调研教师端消息中心的存储与取数口径，实施前需先查清）
3. 退绑通知的措辞与是否允许管理员附一句自定义说明？
4. 教师端「无权访问」类报错要不要一并优化成可读提示（例如区分「已被移出该课程」与「本就不属于该课程」）？这一项与 A 高度相关，建议同批做。
